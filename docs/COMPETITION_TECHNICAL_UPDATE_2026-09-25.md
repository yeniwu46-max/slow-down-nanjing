## 1. 本轮目标

原项目包含智能体、情绪识别、AR、游戏、日记、徽章与数字藏品等多个相对独立的体验。完整产品叙事较丰富，但在数媒竞赛答辩中会稀释核心技术亮点。

本轮将比赛版收敛为“南京文旅智能路线规划”单一主线，重点证明：

1. 路线能够根据时间、天气、体力、文化偏好和开放状态动态调整。
2. 规划结果满足时间与闭馆等硬约束。
3. 每条路线提供可量化、可追溯的推荐理由。
4. 弱网、定位失败和外部接口失败时仍可完成现场演示。

本轮只解除旧功能的入口和比赛主流程依赖，未永久删除原模块文件，方便赛后恢复或拆分复用。

## 2. 比赛版信息架构

比赛版仅保留三个一级入口：

| 入口 | 路径 | 职责 |
|---|---|---|
| 智能路线规划 | `/planner` | 收集路线相关条件并动态生成两条候选路线 |
| 经典路线 | `/map` | 展示项目内置的南京慢行路线与 POI |
| 项目原理与数据说明 | `/about` | 解释数据模型、规划逻辑、数据来源和非实时边界 |

首页和主导航不再暴露智能体、情绪分析、手势控制、沉浸体验、游戏、日记、账户、徽章、数字藏品与非必要分享功能。

## 3. 规划输入模型

比赛版只采集与路线决策直接相关的信息：

| 字段 | 类型 | 作用 |
|---|---|---|
| 起点 | 指定 POI / 设备定位 / 南京默认起点 | 计算首段步行距离；定位失败时降级 |
| 候选地点 | 2–5 个 POI | 限定本次规划搜索空间 |
| 剩余时间 | 45–240 分钟 | 路线总时间硬上限 |
| 步行能力 | 轻松 / 正常 / 较强 | 调整步行时间和体力成本 |
| 路线偏好 | 效率 / 风景 / 文化 | 调整候选路线评分权重 |
| 天气 | 晴 / 多云 / 雨 | 改变室内、遮蔽和户外景观点权重 |
| 出发时间 | 分钟级时间 | 校验到达、停留和闭馆时间 |
| 动态条件 | 临时关闭 / 避开拥挤 / 夜游 | 触发过滤和二次排序 |

语音、照片和情绪文本不再作为路线规划的输入。

## 4. 路线数据模型

### 4.1 POI

`MapPoi` 在基础名称、坐标和分类之上新增：

- 建议停留时间 `suggestedStayMinutes`
- 文化主题标签 `cultureTags`
- 室内/室外属性 `venueType`
- 体力消耗等级 `energyLevel`
- 雨天适宜度 `rainyDaySuitability`
- 休息设施 `restFacilities`
- 无障碍说明 `accessibility`
- 开放时间 `operatingHours`
- 数据来源及核验时间 `dataSources`

当前 23 个 POI 均已补齐上述字段。开放时间、场地属性和体验评分用于比赛算法演示，其中标有“样本”的字段不是场馆实时状态。

### 4.2 道路边

路网边新增：

- 步行时间 `walkingMinutes`
- 景观评分 `scenicScore`
- 遮阴或避雨程度 `shelterScore`
- 拥挤成本 `crowdCost`
- 体力成本 `energyCost`
- 夜间适宜性 `nightSuitability`

这些指标支持同一组地点在不同情境下生成不同顺序或不同取舍。

### 4.3 路线输出

`MapRoute` 新增：

- 分站到达、离开和停留计划 `scheduledStops`
- 未纳入路线的地点 `omittedPoiIds`
- 预计完成时间 `completionTime`
- 数据更新时间与状态 `dataUpdatedAt`、`dataStatus`
- 计算时间与完成时间戳 `calculationMs`、`calculatedAt`
- 量化指标与解释列表 `metrics`、`explanations`

主要类型定义位于 `src/lib/map/types.ts`，规划选项位于 `src/lib/map/planning.ts`。

## 5. 路线计算与动态重算

核心实现位于 `src/lib/map/recommend.ts`。

### 5.1 搜索策略

1. 对最多 5 个候选点生成有序子集，而不是强制全部到访。
2. 临时关闭地点在搜索前直接过滤。
3. 计算起点到首站及各 POI 间的步行段，并缓存重复路段。
4. 为每个候选顺序生成到达、停留和离开时间。
5. 淘汰超过时间预算或无法在闭馆前完成的候选。
6. 分别按效率和体验评分选出两条路线。

时间预算和开放状态属于硬约束；天气、文化、景观、拥挤、夜间适宜性和体力属于排序权重。

### 5.2 动态触发条件

以下变化会在输入稳定后自动重新计算：

- 天气变化
- 剩余时间变化
- 地点临时关闭或恢复
- 用户取消或增加地点
- 步行能力变化
- 效率、风景或文化偏好变化
- 出发时间、避拥挤和夜游状态变化

界面会显示触发原因、数据更新时间和本次计算耗时。计算发生在浏览器本地，不依赖大模型或远程路径服务。

### 5.3 评分原则

- 效率方案优先总时长与步行距离，同时在恶劣天气下允许为明显更合适的地点做小幅调整。
- 体验方案增加景观、雨天适宜性、道路遮蔽、文化主题、低拥挤和夜间适宜性权重。
- 文化偏好会影响文化地点的选择和排序，而不是只改变文案。
- 当前坐标作为真实起点参与首段计算，不再暗中强制最近 POI 为第一站。

## 6. 可解释输出

结果页同时展示：

- 路线地图
- 总距离
- 步行时间
- 游览时间
- 总用时与预计完成时间
- 每站到达、停留和离开顺序
- 数据更新时间、数据状态和计算耗时
- 两条路线的距离、步行、游览、景观与拥挤成本对比

推荐理由根据实际结果生成，例如：

- 比体验路线少走多少公里
- 哪些地点因临时关闭被排除
- 哪些地点无法在闭馆前完成
- 雨天室内或半室内停留占比
- 覆盖的文化主题
- 休息设施数量
- 样本拥挤成本相对变化

解释内容只引用本次路线实际使用的指标，避免出现与路线结果脱节的固定文案。

## 7. 数据真实性约定

界面严格区分以下状态：

| 状态 | 界面含义 |
|---|---|
| 实时天气 | 本次成功调用天气接口获得 |
| 缓存天气 | 先前请求结果，显示缓存状态和时间 |
| 兜底天气 | 固定南京演示数据，仅用于接口失败 |
| 项目样本 | 场馆、道路、拥挤和体验指标的本地演示数据 |

“拥挤成本”“开放时间样本”“体力成本”等历史估计数据不得描述为实时客流或官方实时开放状态。

## 8. 弱网与异常处理

### 8.1 天气失败

- 请求设置超时。
- 优先使用仍可解释的缓存结果。
- 缓存不可用时使用固定南京兜底快照。
- 页面明确标注数据来源状态。

### 8.2 定位失败

- 浏览器拒绝定位或不支持定位时自动切换南京默认起点。
- 用户也可以主动选择南京默认起点。
- 默认起点仍参与首段距离和时间计算。

### 8.3 地图失败

- 底图使用无需 API Key 的 OpenStreetMap 瓦片样式。
- 地图样式内保留本地纸色背景；瓦片失败时 POI 和路线仍可展示。
- 连续瓦片错误会显示“弱网模式”，不会阻断路线规划。
- 地图初始化失败时提供重试操作，并保留已经计算的路线数据。
- 移除远程 glyph URL，减少字体服务不可用造成的控制台警告。

### 8.4 手机布局

规划面板在手机端采用可滚动底部面板，最大高度使用动态视口单位并包含安全区间距，地图仍保留在背景中。已使用 390 × 844 视口完成视觉检查。

## 9. 固定验收场景

以下数据为 2026-09-25 本地浏览器实测，计算耗时会因设备略有变化：

| 场景 | 主要结果 | 总时间 | 本地计算耗时 |
|---|---|---:|---:|
| 雨天、低体力、45 分钟 | 雨天效率方案选择鸡鸣寺；切换晴天后改选台城 | 28 / 26 分钟 | 1 ms |
| 六朝文化、部分场馆即将闭馆 | 玄武湖 → 鸡鸣寺 → 总统府；排除无法在闭馆前完成的台城、南京博物院 | 109 分钟 | 2 ms |
| 周末傍晚、避开拥挤、城市夜游 | 两条可行路线；舒适路线样本拥挤成本低 18% | 133 / 139 分钟 | 2 ms |

额外动态测试：

- 将总统府标记为临时关闭后，路线在 1 ms 内重算并从行程中移除。
- 时间预算从 45 分钟增加到 60 分钟后，路线从单点扩展为鸡鸣寺 → 台城，总时间 47 分钟。
- 取消地点、切换文化偏好均能触发 1 ms 级重新规划。

所有实测路线均未超过用户预算；闭馆地点不会被安排在无法完成游览的时间段。

## 12. 当前边界与下一阶段

- 场馆开放时间、拥挤度、体力与体验评分目前是有来源标识的项目样本，不是实时城市数据。
- 路径几何来自项目本地路网与直连首段，尚未接入生产级步行导航服务。
- 当前搜索上限为 5 个候选点，适合竞赛演示；若扩展到城市级 POI，需要改为启发式搜索或分层规划。
- 旧功能代码仍保留在仓库，但不属于比赛版运行主链路。
- 下一阶段建议补充算法对照实验、数据来源附录和答辩演示脚本。
