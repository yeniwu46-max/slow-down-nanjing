# 《文脉慢行·智游金陵》生产演示文字稿

> 建议时长：7–9 分钟
>
> 演示路线：主页 → 智能路线规划 → 动态重算 → 算法对照 → 文化叙事 → 项目原理
> 讲述原则：屏幕负责展示结果，讲解负责说明判断。不要逐字朗读界面。

## 一、作品标题

**文脉慢行·智游金陵——基于语义理解与文化知识图谱的南京智能文旅路线规划系统**

一句话定位：

**它不是替游客找一条更快的路，而是在有限时间里，计算一条更适合这个人、也更能读懂南京的路。**

## 二、开场与作品简介（约 50 秒）

各位评委老师好，我们的作品叫《文脉慢行·智游金陵》。

我们关注的是一个很具体的问题：今天的旅行软件很擅长告诉人们“怎么更快到达”，却很少回答“这段时间究竟值得怎样使用”。当游客只有一个小时，正在下雨，体力一般，又想了解六朝文化时，单纯的最短路径并不能给出好的答案。

因此，我们把路线规划重新定义为一个带时间窗、文化目标和个体状态的决策问题。系统会理解游客的一句话需求，结合剩余时间、步行能力、天气、开放状态和文化兴趣，在南京的真实步行路网上生成两条可比较的路线。每个结果都说明路线顺序、完成时间、文化覆盖和选择原因，并在条件变化后立即重算。

作品当前覆盖 23 个南京核心文旅地点，连接六朝、明代、民国、秦淮、佛教和金陵山水等文化主题。核心规划、语义理解和文化叙事可以离线运行，适合比赛现场，也具备继续产品化的基础。

## 三、创作来源与创作思路（约 55 秒）

这个创意来自我们对“打卡式旅行”的反思。

南京的文化并不是按景点列表存在的。鸡鸣寺、台城和玄武湖在地图上是三个坐标，在历史中却共享六朝都城的空间记忆；颐和路、总统府和 1912 也不是三个互不相干的目的地，它们共同构成南京近代城市生活的一条线索。

问题在于，普通地图保存了空间关系，却没有保存文化关系；普通攻略写出了文化故事，却不能根据时间、天气和体力实时调整。

我们的创作思路，是把这两部分放进同一个计算系统：一边用真实步行路网解决“能不能走完”，另一边用文化知识图谱解决“为什么这样走”。“宁可慢一点”不是降低效率，而是拒绝把景点数量当作唯一目标。算法需要学会取舍，把有限时间留给真正符合游客兴趣的地点。

## 四、功能演示文字稿

### 1. 进入智能规划（约 30 秒）

【操作】在主页点击“智能路线规划”。

现在进入路线规划页。这里保留的输入都直接影响路线：从哪里出发、想去哪些地点、还剩多少时间、步行能力，以及更重视效率、风景还是文化。天气、出发时刻、避开拥挤和城市夜游，也会进入规划条件。

左侧是南京地点与经典路线，右侧是本次个性化规划。地图不是结果的装饰，它会跟随路线选择同步更新。

### 2. 自然语言理解（约 50 秒）

【操作】输入：**“想看六朝遗迹，少走路，雨天多安排室内。”** 点击“理解并推荐地点”。

这里没有让大模型直接编一条路线。系统先使用本地 BGE 中文语义模型，把这句话转换成地点相关度；同时，规则层会识别“少走路”和“雨天室内”这样的明确约束。

也就是说，语义模型负责理解文化兴趣，结构化规则负责守住体力、天气和时间。模型可以影响偏好，但不能覆盖闭馆时间和总预算。这种分层设计，让系统既有语言理解能力，又不会把关键约束交给不可控的黑箱判断。

【操作】从推荐结果中加入 2–5 个地点。

系统只做推荐，不会替用户擅自加入地点。最终候选集仍由用户确认。

### 3. 设置约束并生成路线（约 50 秒）

【操作】选择“南京默认”起点；设置 2 小时、轻松走、文化偏好、雨天；点击生成路线。

系统开始在候选地点之间计算可行顺序。总时间由三部分构成：步行、停留和开馆前等待。任何一个地点如果无法在闭馆前完成，或者使总时长超过预算，都会被排除或调整顺序。

结果同时给出效率路线和体验路线。我们没有把“智能”包装成一个无法比较的结论，而是把总距离、步行时间、游览时间、文化覆盖和文本匹配放在同一张量化表中。游客可以看到每一种取舍的代价。

### 4. 展示可解释结果（约 45 秒）

【操作】展开其中一条路线，指向路线顺序、推荐理由和文化叙事链。

这条路线不是只有一条折线。系统会说明每一站的预计到达时刻、停留时间和完成时间，也会给出选择依据，例如减少步行、提高室内停留比例、覆盖重点文化主题，或者避开无法按时完成的场馆。

文化叙事按照实际游览顺序生成。系统从知识图谱中寻找相邻地点之间已经核验的时期、人物、事件或主题关系。能找到可靠联系时，它会生成承接；找不到时就保留独立站点故事，不强行编造过渡。

### 5. 动态重新规划（约 55 秒）

【操作】依次修改天气、剩余时间或临时关闭状态。

现在把天气从多云改为雨天，或者缩短剩余时间。路线会立即重新计算。系统复用已经完成的语义结果，不会在每次条件变化时重新加载模型，因此动态调整保持在毫秒级。

如果某个地点临时关闭，地点会从可行集合中移除；如果时间减少，系统优先保留与用户文化需求更匹配的地点；如果切换为低体力，步行成本会提高，路线顺序和地点数量也可能随之变化。

这体现了作品的核心能力：它生成的不是一次性的推荐，而是一套可以响应环境变化的路线决策。

### 6. 算法对照（约 45 秒）

【操作】指向“算法对照”。

这里同时展示三类结果。

基准路线按照用户勾选顺序执行，用来代表没有智能排序的方案；智能路线综合语义、文化、天气和体验评分；最优验证路线则对不超过 5 个地点的全部子集和顺序进行精确枚举。

精确解不替代智能路线。它的作用是验证智能路线有没有少完成地点，以及在完成地点数相同时，与最短可行时间还相差多少。这样，我们既保留了个性化体验，也给算法提供了可以核验的参照系。

### 7. 文化知识图谱（约 45 秒）

【操作】进入“项目原理”，搜索“六朝”或点击鸡鸣寺节点。

这是系统的文化知识层。地点不再只有名称和坐标，而是与历史时期、人物、事件、文化主题和遗产类型相连。点击节点可以查看文化关系，也可以继续展开相邻实体。

当前 23 个 POI 都建立了可追溯的文化关系。外部史实、项目编目和原创表达分开存储，路线叙事只使用已有证据，不让生成式语言模型自由补写历史。知识图谱同时参与文化覆盖计算，因此它不是展示用的装饰，而是路线决策的一部分。

## 五、技术介绍（约 80 秒）

系统采用 Next.js 16、React 19 和 TypeScript 构建，地图层使用 MapLibre GL。整体技术链分为五层。

第一层是意图理解。浏览器通过 Web Worker 加载量化后的 `bge-small-zh-v1.5`，对自然语言需求进行 512 维向量检索。模型在本地运行，避免上传用户文本，也避免推理阻塞地图交互。

第二层是文化知识。系统使用离线 JSON-LD 建立南京文化知识图谱，把地点与主题、时期、人物、事件和文化遗产连接起来。文化覆盖率和叙事链都从这套图数据中计算。

第三层是真实路网。23 个 POI 之间的 529 个地点对由 Valhalla 基于 OpenStreetMap 步行网络生成，路线计算使用路网距离和步行时间，不再依赖直线距离估计。

第四层是约束规划。开放时间、闭馆时间、等待、停留、总预算和临时关闭属于硬约束；语义、文化、天气、景观、拥挤和夜间适宜性属于软目标。两者分开处理，避免偏好评分破坏可行性。

第五层是解释与验证。结果会生成路线顺序、量化差异和文化叙事，并使用精确枚举解检查完成地点数和最优时间差。Valhalla、OR-Tools 和 GraphHopper 可以作为外部技术服务，但正式演示不依赖它们在线运行。

## 六、核心创新点（约 50 秒）

第一，系统把自然语言偏好转换成可计算的路线条件。它理解“民国建筑”“少走路”和“雨天室内”的方式并不相同：文化兴趣进入语义评分，明确限制进入结构化约束。

第二，文化知识图谱进入了规划目标。路线不只追求距离，还计算文化主题覆盖，并根据实际顺序生成有证据的城市叙事。

第三，规划过程同时支持时间窗、体力、天气和动态事件。用户条件发生变化后，系统复用语义缓存进行快速重算。

第四，作品建立了完整的算法证据链。基准、智能与精确解可以直接比较，BGE、知识图谱和天气规则可以分别关闭做消融实验，所有结论都能回到原始 CSV 和固定场景复现。

## 七、实验结果（约 45 秒）

我们建立了 60 套固定场景，覆盖六朝、民国、秦淮、明城墙、博物馆、佛教、低体力、无障碍和夜游等主题，并运行 Full、No-BGE、No-KG、No-Weather 四组实验，共得到 240 组功能结果。

在精确求解器判定可行的 56 个场景中，路线生成率为 100%；4 个故意构造的不可行场景全部被正确拒绝。超预算、闭馆和临时关闭地点违规率均为 0%。

性能测试包含 1,200 次动态重算，当前测试环境下 P95 为 8.11 毫秒，远低于 500 毫秒的现场目标。消融结果也如实保留了零提升和负结果，没有只挑有利案例。

## 八、应用价值（约 40 秒）

这套能力可以用于城市文旅平台、景区导览、博物馆群联动和研学路线设计。对老年游客、亲子家庭、行动不便人群和短时过境游客，它可以把体力、无障碍和剩余时间直接纳入路线。

更重要的是，这套方法不只适用于南京。替换城市路网、POI 数据和文化知识图谱后，同一套规划框架可以迁移到西安、苏州、泉州等历史文化城市。城市的内容不同，决策结构可以复用。

## 九、运行环境（约 25 秒）

作品采用 B/S 架构，支持 Windows、macOS 和主流 Linux 系统，推荐使用最新版 Chrome 或 Edge。服务端使用 Node.js 20 及以上环境，生产部署支持 Vercel 或标准 Node.js Web 服务。

BGE 模型、文化知识图谱和步行矩阵可以随离线包部署。天气或在线地图不可用时，系统会切换到缓存数据和南京默认起点，核心规划流程仍可完成。

## 十、结束语（约 25 秒）

《文脉慢行·智游金陵》想解决的并不是“怎样把更多景点塞进一天”，而是怎样在真实限制中，为一个具体的人保留最有价值的城市体验。

我们让地图拥有文化关系，让算法理解人的节奏，也让每一条推荐路线都能说明自己的判断。希望游客离开南京时，记住的不只是走过多少地点，而是终于读懂了一段城市。

## 十一、提交表格可用短文案

### 作品简介

《文脉慢行·智游金陵》是一套面向南京深度文化旅行的可解释智能路线规划系统。作品使用本地 BGE 中文语义模型理解自然语言需求，以文化知识图谱组织地点、时期、人物、事件和文化主题，并在 Valhalla/OpenStreetMap 步行路网上综合开放时间、游览预算、体力、天气、拥挤和夜间条件完成多目标规划。系统支持动态重算、双路线量化比较、文化覆盖分析和有来源的路线叙事。60 套固定场景实验中，可行路线生成率和不可行情形正确拒绝率均为 100%，硬约束违规率为 0%，1,200 次动态重算的 P95 为 8.11 毫秒。

### 创作思路

作品从打卡式旅行的矛盾出发：地图知道地点之间有多远，却不知道它们在文化上为何相连；攻略能够讲故事，却不能根据时间、天气和体力即时调整。我们把真实步行路网和南京文化知识图谱放进同一套规划系统，用硬约束保证路线走得完，用语义与文化评分决定有限时间更值得留给哪里，再按照实际游览顺序生成有证据的叙事链。

### 技术简介

前端基于 Next.js、React、TypeScript 与 MapLibre GL。语义层使用 Web Worker 运行量化 BGE 中文模型；文化层采用离线 JSON-LD 知识图谱；路由层使用 Valhalla 生成的 23×23 步行矩阵；规划层分离时间窗、预算、闭馆等硬约束与语义、文化、天气等软目标；验证层使用基准路线和 ≤5 POI 精确枚举解进行对照。核心资源可离线部署，外部路由和优化服务缺失时不影响正式演示。

### 主要创新

1. 将自然语言文化偏好与结构化硬约束分层处理，避免黑箱模型破坏路线可行性。
2. 将文化知识图谱真正用于路线评分和顺序叙事，而非停留在信息展示。
3. 支持天气、时间、关闭地点和体力变化下的毫秒级动态重算。
4. 建立基准、智能、精确解和三组消融实验组成的可复现算法证据链。

## 十二、答辩追问备用回答

### 为什么不用生成式大模型直接规划？

生成式模型适合语言表达，但不适合独立承担闭馆、预算和时间窗约束。我们的系统让 BGE 负责语义相关度，让确定性求解器负责可行性，再用有来源的模板生成文化叙事。这样更稳定，也更容易解释和复现。

### 你们训练了自己的模型吗？

我们没有把预训练模型包装成自主训练成果。项目使用固定 revision 的 BGE 中文预训练模型，完成本地量化推理、POI 语义文档构建、向量缓存和规划集成。原创工作集中在数据组织、约束建模、图谱联动、解释算法和实验验证。

### 为什么最多选择 5 个地点？

这是产品场景和算法验证共同决定的。慢游半日路线通常不需要大量地点；上限为 5 时，浏览器可以精确枚举全部子集和顺序，给出透明的最优验证结果。扩大到城市级 POI 后，可以切换到 OR-Tools 或分层启发式搜索。

### 数据是实时的吗？

天气支持实时接口、缓存和默认数据三级降级。步行路网是带时间戳的离线快照；开放时间、拥挤和舒适度中的部分字段是项目样本，不描述为实时城市数据。系统在界面和技术文档中保留了来源与数据边界。

### 作品与普通地图导航的区别是什么？

普通导航通常已知目的地，再求一条到达路径。我们的系统需要先从多个候选地点中决定去哪些、按什么顺序、停留多久，并同时满足时间窗、预算和个体偏好。它更接近带文化目标的行程决策，而不是单纯的两点导航。
